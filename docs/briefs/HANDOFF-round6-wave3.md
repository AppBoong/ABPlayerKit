## 3. v0.4.0 출하 전 반드시 처리할 것

### 3-1. 기기 수동 확인 (자동 검증 불가 — 가장 중요)

`docs/briefs/REVIEW-round6-nowplaying.md` §8에 6개 항목이 있다. **시뮬레이터에 PiP가 없어 트랙 G의 자동 검증은 "정책 리듀서 + 바인딩 수명 + 설정 전달"까지만 닿는다.** 그린이지만 기기에서 기능이 죽어 있을 가능성이 가장 높은 지점이다:

1. PiP 실제 시작/렌더링/배경 지속/복원
2. `didEnterBackgroundNotification`과 PiP 자동 활성화 KVO의 순서 (복구 경로는 단위 테스트로 고정돼 있으나 실제 순서는 기기 전용)
3. `.continueAudioOnly`의 실제 배경 오디오 지속 — 데모에 `UIBackgroundModes: audio`가 **아직 없어** 그대로는 시연 불가
4. NowPlaying 잠금화면 표시 및 리모트 커맨드(헤드셋 버튼, 컨트롤 센터)
5. AirPlay 실제 라우팅과 `isExternalPlaybackActive` 관측
6. PiP 활성 중 플레이어가 예기치 않게 소멸하는 시나리오 (설계 §12.4 안전망을 구현하지 않았음 — 코드 경로상 안전해 보이나 미검증)

**릴리스 전 사람이 기기에서 확인해야 한다. R-1 전에 이 목록을 사용자에게 제시하라.**

### 3-2. 커버리지 숫자의 맥락

배지가 92.2%(F 병합 후) → 90.7%(G 병합 후)로 **떨어졌다. 회귀가 아니다.** G가 추가한 PiP/MediaPlayer 경로가 시뮬레이터에서 실행 불가라 커버되지 않는다. Wave 3에서 이 숫자를 볼 때 원인을 알고 볼 것.

### 3-3. 이월 항목 (v0.4.0에 넣지 않기로 확정된 것)

- **S-PiP-1~4** — 편의 API(`ABVideoPlayerWithControls(url:)` 계열) + PiP 조합. `DESIGN-round6-nowplaying.md` §5.4에 4건 묶음 요구사항이 있고 **부분 도입 금지**다. v0.5.0 additive 권고. 현재 문서에는 "PiP는 명시 소유 경로에서만 지원"이 한계로 명시돼 있다.

## 4. 운영 교훈 (Wave 2에서 새로 얻은 것 — HANDOFF-wave2 §4에 더할 것)

Wave 2 브리프에 반영한 기존 교훈(전체 스킴 3회, 게이트 독립 실행, 프롬프트 전송 후 재확인, 즉시 정리)은 **전부 유효했고 실제로 값어치를 했다.** 아래는 이번에 새로 배운 것이다.

### 4-1. 게이트가 구현자 자가 보고의 거짓을 실제로 잡아냈다

트랙 G 구현자는 `RESULT` §6에 "위생 재스캔 결과 출력 없음"이라고 **명시적으로 보고**했으나, 게이트가 같은 명령을 직접 돌리자 `@unchecked Sendable` 1건이 남아 있었다. "게이트는 구현자 보고를 근거로 인정하지 마라"가 추상적 원칙이 아니라 실제로 결함을 잡는 장치임이 확인됐다.

→ **자가 스캔 결과를 보고할 때는 명령의 원본 출력(exit code 포함)을 첨부하게 하라.** 수정 후 트랙 G가 그렇게 했고, 다음 게이트가 그것마저 재실행해 교차 확인했다.

→ 이 사실을 다른 트랙 게이트에도 즉시 전파하니(트랙 C 게이트에 "방금 G에서 이런 일이 있었다"고 알림) 그 게이트가 **diff 기반 스캔과 전체 파일 raw 스캔을 이중으로** 돌렸고, raw 스캔의 오탐 4건(사전 존재 코드)을 diff 0줄 확인으로 정확히 가려냈다. 게이트 간 학습 전파가 효과적이었다.

### 4-2. 리베이스는 게이트 **이전**에 하라

트랙 G·C는 "커밋 → 리베이스 → 게이트 → PR" 순으로 진행했다. 그래야 **게이트의 3회 실행이 곧 트랙 통합 상태의 첫 검증**이 된다. Wave 1에서 트랙들이 자기 타깃만 검증하고 PR을 올렸다가 CI에서 깨진 실패가 전부 자기 타깃 밖에 있었던 그 문제를 로컬에서 먼저 잡는다.

실제로 트랙 G 게이트는 리베이스 후 실행에서 Metrics 스위트가 8건 → 49건으로 늘어난 것을 세어 **리베이스가 제대로 반영됐음을 실행으로 확인**했다. 문서 대조가 아니라 실행 결과로 확인한 것이 좋았다.

### 4-3. 툴체인에 의존하는 판정은 PR CI에 맡겨라

D-10(Style `Sendable`화)은 "로컬에 Xcode 16.4가 없어 CI 툴체인 선검증 불가"를 이유로 이월될 뻔했다. 그러나 **PR CI가 정확히 그 툴체인**이다. 붙여서 올렸더니 통과했고, 이월할 이유가 애초에 없었다.

→ 로컬에서 확정할 수 없다는 이유만으로 이월하지 마라. 거부되면 그 커밋만 들어낼 수 있게 **파일 단위로 분리해 두고** CI에 물어보는 편이 낫다. 실패 비용은 CI 사이클 1회다.

### 4-4. CHANGELOG 충돌은 3트랙 병렬에서 매번 난다

F·G·C가 전부 `### Added`와 `### Migration notes`에 항목을 추가하므로, 리베이스 때마다 같은 자리에서 충돌했다. **전부 순수 추가 충돌이라 양쪽 보존이 항상 정답**이었다. 해결 후에는 각 트랙의 대표 키워드를 grep해 유실이 없는지 확인하는 습관이 유효했다.

### 4-5. 게이트가 "비차단"으로 분류한 실재 결함을 그냥 넘기지 마라

트랙 C 게이트는 VoiceOver 배지 델타 결함을 코드 추적으로 재현했으나 영향 범위가 좁아 비차단으로 판정했다. 논거는 타당했지만, **설계의 서면 완료 기준("표시 시간 == 프리젠터 계산값 == 배지 델타")을 문자 그대로 충족하지 못한 것**은 사실이었다.

C는 병합 순서상 마지막이라 **일정 비용이 0**이었으므로 수정을 지시했고, 결과적으로 세 시크 경로 전부에 배지 델타 단언이 추가됐다(원래 어느 경로에도 없었다).

→ 판단 기준: 비차단이라도 **일정 비용이 없고 원인이 특정돼 있으면 닫아라.** 대신 수정이 다른 불변식(여기서는 I-C9)을 깨지 않을 조건을 브리프에 명시하고, "고치는 것이 불변식을 깨지 않고는 불가능하면 고치지 말고 분석을 보고하라"는 탈출구를 함께 줄 것.

### 4-6. CI 실패는 재실행 전에 "무엇이 실제로 테스트되는가"를 대조하라

TSan 잡이 하루 3회 실패했다. 매번 **data race 0건 + `waitUntil` 타임아웃**이었다. 트랙 C PR에서 2연속 실패했을 때, `git diff origin/main -- <TSan 잡이 실제로 테스트하는 경로>`가 **0줄**임을 확인한 것이 결정적이었다 — C의 코드는 그 잡이 돌리는 것에 영향을 줄 수 없다.

원인은 헬퍼의 고정 2초 데드라인이 TSan 계측(5~15배 감속) + 3코어 러너에서 **"느림"을 "멈춤"으로 오판**한 것이었다. PR #11이 `ABPLAYERKIT_WAIT_SCALE`(기본 1, TSan 잡만 `TEST_RUNNER_` 접두사로 6)로 수정했고, **리베이스 후 같은 브랜치가 통과**해 진단이 검증됐다.

→ 재실행 반복은 "그린이 나올 때까지 돌리기"이지 해결이 아니다. 2회 연속 실패하면 재실행을 멈추고 원인을 대조하라.
→ 타임아웃을 일괄로 늘리지 마라. 진짜 교착도 같은 배수로 늦게 발견된다. **느린 것이 확실한 환경에서만** 늘려라.

### 4-7. 메인 체크아웃에서 `git checkout <ref> -- .`를 쓰지 마라

파일 내용을 보려다 인덱스에 origin/main 전체를 스테이징해 버렸다(로컬 main이 뒤처져 있었으므로 대량 변경으로 보였다). 다행히 로컬 변경이 없어 `reset --hard origin/main`으로 무해하게 복구됐다.

→ 다른 ref의 파일을 볼 때는 `git show <ref>:<path>`를 써라. worktree가 여러 개일 때 메인 체크아웃의 상태를 건드리는 것은 특히 위험하다.
