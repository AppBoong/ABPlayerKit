# 기기 수동 확인 체크리스트

시뮬레이터가 실행할 수 없는 기능을 실기기에서 확인하기 위한 목록이다. 릴리스 전에 사람이 직접 수행한다.

**왜 이 목록이 필요한가.** 시뮬레이터에는 Picture in Picture가 없고, 잠금화면도, AirPlay 수신 경로도 없다. 그래서 이 영역의 자동 검증은 "정책 리듀서 + 바인딩 수명 + 설정 전달"까지만 닿는다. CI가 전부 그린인 것과 기기에서 기능이 살아 있는 것은 **별개의 주장**이며, 이 목록은 그 간극을 메우는 유일한 수단이다.

---

## 사전 준비

1. Xcode에서 `Examples/ABPlayerKitDemo/ABPlayerKitDemo.xcodeproj`를 연다.
2. `ABPlayerKitDemo` 타깃 → **Signing & Capabilities** → **Team**을 선택한다.
   프로젝트에 `DEVELOPMENT_TEAM`이 비어 있으므로 이 단계가 반드시 필요하다. 개인 팀이라도 무방하다.
3. iOS 17.0 이상 실기기를 연결하고 실행 대상으로 선택한 뒤 ⌘R.

데모는 네트워크 스트림(Apple HLS / W3C MP4)을 재생하므로 인터넷 연결이 필요하다.

**AirPlay 항목에는 실제 수신기가 별도로 필요하다** — Apple TV, AirPlay 2 지원 스피커, 또는 macOS의 AirPlay 수신 기능.

## 1. PiP 실동작

**확인 대상** — PiP가 실제로 시작되고, 렌더링되고, 앱이 배경으로 가도 계속 재생되고, 앱으로 복귀할 때 원래 화면으로 되돌아오는가.

**자동 검증이 닿은 범위** — 정책 리듀서, 세션 바인딩 수명, `AVPictureInPictureController` 설정 전달까지. 실제 PiP 창이 뜨는지는 **전혀 검증되지 않았다.**

**절차**
1. 데모의 **Device** 탭으로 이동한다.
2. **Play** 버튼으로 재생을 시작하고 영상이 보이는지 확인한다.
3. **Picture in Picture** 섹션의 **Start PiP** 버튼을 누른다.
4. 홈 제스처로 앱을 배경으로 보낸다.
5. PiP 창의 복귀 버튼을 눌러 앱으로 돌아온다.

**통과** — 3에서 PiP 창이 뜨고 영상이 그 안에서 재생된다. 4에서 앱이 사라져도 PiP 창이 남아 재생을 계속한다. 5에서 앱이 열리며 영상이 원래 화면에서 이어진다.

**실패 징후** — 버튼을 눌러도 아무 일도 없다(`isPossible`이 false일 수 있다), PiP 창은 뜨는데 검은 화면이다, 배경 전환 시 PiP가 함께 사라진다, 복귀 시 영상이 처음부터 재생되거나 정지해 있다.

**실패 시 기록할 것** — 화면에 표시되는 `isPossible` / `isActive` / `lastFailure` 값. `lastFailure`에 원인이 담긴다.

## 2. 배경 진입과 PiP 자동 활성화의 순서

**확인 대상** — `didEnterBackgroundNotification`과 PiP 자동 활성화 KVO 중 어느 것이 먼저 도착하는지. 순서가 뒤바뀌면 배경 정책이 PiP를 죽인 뒤 PiP가 켜지는 상황이 생길 수 있다.

**자동 검증이 닿은 범위** — 복구 경로 자체는 단위 테스트로 고정돼 있다. **실제 도착 순서는 기기에서만 관측된다.**

**절차**
1. **Device** 탭의 **Starts automatically from inline** 토글을 켠다.
2. 재생을 시작한다. **Start PiP는 누르지 않는다** — PiP를 수동으로 켜지 않는다.
3. 홈 제스처로 앱을 배경으로 보낸다.

**통과** — 배경 전환과 동시에 PiP가 자동으로 시작되고 재생이 끊기지 않는다.

**실패 징후** — PiP가 뜨긴 하는데 **일시정지 후 재개**되며 눈에 띄게 끊긴다. 이 경우 복구 경로가 동작한 것이며, 설계상 예상된 동작이므로 치명적이지는 않지만 **관측되면 반드시 기록한다.** 문서에도 "복구 경로가 짧은 일시정지-재개로 드러날 수 있다"고 적혀 있다.

**치명적 실패** — PiP가 아예 시작되지 않거나, 시작됐다가 즉시 사라진다.

## 3. `.continueAudioOnly` 배경 오디오

> 이 경로는 v0.4.0에서 **새로 만들어졌고 실기기에서 한 번도 실행된 적이 없다.** 우선순위가 높다.

**확인 대상** — 배경 정책이 `.continueAudioOnly`일 때 앱이 배경으로 가도 오디오가 계속 나는가.

**동작에 필요한 세 조건** — `UIBackgroundModes`에 `audio` 포함(데모에 선언돼 있음), `audioSessionPolicy != .unmanaged`, `backgroundPolicy == .continueAudioOnly`. **셋이 동시에 맞아야 한다.** 데모에서 피커를 고르면 오디오 세션은 자동으로 관리형으로 전환되므로 사용자가 따로 할 일은 없다.

**절차**
1. **Playback grade**를 `Current`로 선택한다.
2. 재생을 시작하고 **소리가 나는지** 확인한다. **Muted** 토글이 꺼져 있어야 한다.
3. **Live configuration** → **Background policy** → `Continue audio only`를 선택한다.
4. 홈 제스처로 앱을 배경으로 보낸다. 앱을 종료하지 않는다.

**통과** — 화면이 사라져도 소리가 계속 난다. 앱으로 돌아오면 영상이 이어서 재생된다.

**실패 징후** — 배경 전환 즉시 소리가 끊긴다.

**실패 시 확인할 것** — 기기의 **설정 → 일반 → 백그라운드 앱 새로 고침**이 꺼져 있지 않은지, 무음 스위치가 켜져 있지 않은지 먼저 배제한다.

## 4. NowPlaying 잠금화면과 리모트 커맨드

**확인 대상** — 잠금화면·제어 센터에 재생 정보가 뜨고 버튼이 실제로 동작하는가.

**자동 검증이 닿은 범위** — `MPRemoteCommandEvent`를 테스트에서 만들 수 없어 **순수 라우터까지만** 검증됐다. 실제 커맨드 전달은 미검증이다.

> **반드시 두 구성 모두 확인할 것.** 최종 게이트가 잡은 결함이 정확히 이 지점이었다 — 문서가 활성화 조건을 하나만 제시해 기본 구성으로는 다음/이전 트랙 핸들러가 **조용히 설치되지 않았다.** 문서는 고쳐졌고, 이 확인이 그 수정을 실증한다.

### 4-A. 기본 `commands`

**절차**
1. **Playback grade** = `Current`, 재생 시작.
2. **Now Playing** 그룹의 **"Show on lock screen / Control Center"** 토글을 켠다.
3. 기기를 잠그거나 제어 센터를 연다.

**통과** — 제목(`Apple HLS` 또는 `Sample MP4`)이 표시되고 다음이 동작한다: 재생/일시정지, 15초 앞뒤 건너뛰기, 스크러버, 헤드셋 버튼의 재생/일시정지 토글.

**예상되는 정상 동작** — 다음/이전 트랙·배속 버튼은 **보이지 않는다.** `ABRemoteCommandSet.default`가 이 셋을 제외하기 때문이며, 이것이 의도된 동작이다.

### 4-B. 확장 `commands`

**절차**
1. **Playback** 탭의 **Now Playing** 그룹에서 **Extended commands** 토글을 켠 뒤 4-A를 반복한다.
2. 잠금화면 또는 제어 센터에서 **다음 트랙**과 **이전 트랙**을 몇 번 누른다.
3. 잠금을 풀고 **Playback** 탭으로 돌아와 **Track navigation** 줄의 `Next: N / Previous: N` 값을 읽는다.

**통과** — 다음/이전 트랙 버튼이 나타나고, 누른 횟수만큼 **Track navigation** 카운터가 올라간다. 배속 커맨드도 노출된다.

> **잠금화면 자체는 아무 반응도 하지 않는 것이 정상이다.** 이 라이브러리에는 큐 개념이 없어 트랙 이동 핸들러는 재생 정보를 다시 발행하지 않는다. 제목도 시간도 그대로다. 커맨드가 전달됐다는 증거는 **오직 이 카운터뿐**이므로, 잠금화면만 보고 판정하면 정상 동작을 실패로 기록하게 된다.

**실패 징후** — 옵션을 켜도 버튼이 나타나지 않는다(활성화 조건이 여전히 충족되지 않은 것이다), 또는 버튼은 보이는데 카운터가 그대로다(핸들러가 설치되지 않은 것이다 — 이 항목이 잡아내려는 바로 그 증상).

## 5. AirPlay 라우팅

**확인 대상** — 실제 AirPlay 수신기로 라우팅되고 `isExternalPlaybackActive`가 `true`로 관측되는가.

**필요한 것** — 실제 수신기(Apple TV, AirPlay 2 스피커, macOS AirPlay 수신). 시뮬레이터로는 불가능하다.

**절차**
1. 기기와 수신기를 같은 네트워크에 둔다.
2. 데모의 **Device** 탭에서 재생을 시작한다.
3. 제어 센터 또는 **AirPlay** 섹션의 **Route picker**에서 수신기를 선택한다.
4. 화면에 표시되는 **isExternalPlaybackActive** 값을 관측한다.

**통과** — 영상/오디오가 수신기로 넘어가고 `isExternalPlaybackActive`가 `true`가 된다. 라우트를 기기로 되돌리면 `false`로 돌아온다.

**실패 징후** — 라우팅은 되는데 `isExternalPlaybackActive`가 `false`로 남는다, 또는 `allowsExternalPlayback`를 껐는데도 영상이 넘어간다.

**함께 볼 것** — **AirPlay** 섹션의 **Uses external playback while screen active** 토글과 **Aspect / Aspect fill** 피커로 `usesExternalPlaybackWhileExternalScreenIsActive`와 `externalPlaybackVideoGravity`를 바꿔가며 화면 채움 방식이 달라지는지 확인한다.

## 6. PiP 활성 중 플레이어 소멸

**확인 대상** — PiP가 켜진 상태에서 플레이어가 예기치 않게 사라질 때 안전하게 정리되는가.

**중요** — 설계 §12.4의 안전망(바인딩된 플레이어의 `avPlayer`가 `nil`이 되면 세션을 강제 `stop()`)은 **구현되지 않았다.** 코드 경로 분석상으로는 안전해 보이나 **미검증**이며, 이 항목은 그 가정을 실증하는 것이다.

**절차**
1. **Device** 탭에서 PiP를 시작한다.
2. 앱을 배경으로 보내 PiP만 남긴다.
3. **PiP 창의 복귀 버튼을 쓰지 말고** 앱으로 돌아온다 — 홈 화면의 아이콘이나 앱 전환기를 쓴다. PiP 창이 앱 위에 계속 떠 있어야 한다.
4. 플레이어를 소멸시키는 조작을 한다 — **Destroy the player** 섹션의 **Swap source** 또는 **Release player** 버튼.

> 3에서 **복귀 버튼을 누르면 PiP가 종료된다.** 그 상태로 4를 하면 PiP가 꺼진 채 플레이어를 소멸시키는 것이라 이 항목이 검사하려는 상황이 아니며, 아무 일도 일어나지 않는 것을 통과로 착각하게 된다. 4를 누르기 전에 **PiP 창이 아직 떠 있는지 반드시 눈으로 확인한다.**

**통과** — PiP 창이 깔끔하게 닫히거나, 남더라도 앱이 죽지 않는다.

**실패 징후** — 앱이 크래시한다, PiP 창이 멈춘 프레임으로 남아 닫히지 않는다, 앱 복귀 후 조작이 불가능하다.

**실패 시** — 재현 절차를 정확히 기록한다. 설계 §12.4 안전망을 구현할 근거가 된다.

## 실패를 발견했을 때

기록할 것:
- 어느 항목의 어느 단계에서 실패했는가

- 기기 모델과 iOS 버전
- 재현되는가, 아니면 한 번만 발생했는가
